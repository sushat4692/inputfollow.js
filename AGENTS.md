# AGENTS.md

Guide for AI agents (opencode, etc.) working in this repository.

## Project overview

- **inputfollow.js**: a TypeScript front-end library that provides form validation and input limiting (the standalone version of the jQuery plugin)
- Versioning: gitflow branch strategy
- Target: browsers (ES6+), built as both UMD and ESM
- Dependencies: none (the validators are implemented in-house; the e-mail regex is adapted from zod's regex, but zod is not a dependency)

## Branch strategy (gitflow)

- `master`: released code only (release tags `v0.0.x`)
- `develop`: integration branch. Always create feature branches from the latest `develop`
- `feature/*`: feature branches (branch from `develop`, merge back into `develop` when done)
- `release/v0.0.x`: release preparation branches (branch from `develop`, merge into both `master` and `develop`)
- `hotfix/*`: urgent fix branches (branch from `master`)

Always create a new branch from the latest `develop` before starting work. Never
merge a `feature/*` branch directly into `master`.

Follow `.opencode/skills/release/SKILL.md` for release work (creating
`release/vX.Y.Z` through publishing to npm). **`demo/js/inputfollow*.js` must be
regenerated with `npm run build && npm run make:demo:js` and committed on every
release** so that the version banner and the latest code stay in sync.

## Directory structure

```
src/             … implementation
  index.ts       … entry point (exports InputFollow and the public types)
  types.ts       … type definitions and runtime validators (InitialParam, Rule, ...)
  convert/       … input value conversion (Code, Number)
  validate/      … validation logic (Required, Email, Number, Code, Equal, custom)
  model/Element.ts … creates and manages a field controller
  utils/Tag.ts   … element helpers
CHANGELOG.md     … changelog (source of truth, synced into the docs site)
CHANGELOG.ja.md  … Japanese changelog
demo/            … standalone demo page (scss → css, copies built JS from dist)
site/            … documentation site (Astro + Starlight, npm workspaces member)
  astro.config.mjs … Starlight / starlight-typedoc config (base: /inputfollow.js)
  src/content/docs … English docs (root locale) and Japanese docs under ja/
  src/components/LiveDemo.astro … interactive demos embedded in the docs
styles/          … optional stylesheet shipped as dist/inputfollow.css
types/           … generated type definitions (do not edit)
dist/            … build output (gitignored)
```

## Generated files (do not inspect or edit)

- `types/` is committed but generated by the build. Hand-editing it is not necessary
- `site/src/content/docs/api/` and `site/src/content/docs/ja/api/` are generated by starlight-typedoc from the TSDoc in `src/` (gitignored, do not edit)
- `site/src/content/docs/changelog.md` and `site/src/content/docs/ja/changelog.md` are generated from `CHANGELOG.md` / `CHANGELOG.ja.md` by `scripts/sync-changelog.mjs` (gitignored, do not edit)
- To change them, edit the source (`src/` TSDoc comments and type definitions) and regenerate with `npm run docs` or `npm run build`
- `dist/`, `.rollup.cache/`, `tsconfig.tsbuildinfo`, `site/dist/` and `site/.astro/` are gitignored build artifacts; never commit them

## Documentation site

- English is the primary language (`site/src/content/docs/` root). Japanese lives under `site/src/content/docs/ja/`
- Each feature page embeds a minimal form with `LiveDemo.astro` (the standalone `demo/` is for local checks)
- The changelog pages are synced from the root `CHANGELOG.md` / `CHANGELOG.ja.md` by `npm run changelog:sync` (the `docs` scripts run it automatically)
- Published at https://sushat4692.github.io/inputfollow.js/ (`.github/workflows/deploy.yml` deploys `site/dist` to the gh-pages branch on `master` push)
- Use relative links inside content components so they resolve under `base: '/inputfollow.js'`

## Tests

- `test/unit/`: jsdom unit/integration tests (validation, conversion, types, the whole InputFollow flow)
- `test/browser/`: real-browser integration tests with Vitest Browser Mode (playwright provider, chromium, headless)
- Add the relevant unit tests for new features and bug fixes, and browser tests for behavior that should be verified in a real browser
- The first browser test run requires `npx playwright install chromium`
- Configuration lives in `vitest.config.ts` (two projects: unit / browser)

## Coding conventions

- TypeScript and oxfmt settings: `singleQuote: true` / `semi: false` / `printWidth: 80` / `tabWidth: 4` (see `.oxfmtrc.json`)
- Unused variables are allowed with a `_` prefix (`.oxlintrc.json` no-unused-vars setting)
- Add TSDoc comments such as `@public` to the public API. When types change, regenerate the API reference with `npm run docs` and check the result
- Export from `src/index.ts` (the `InputFollow` function and the public types)

## Implementation notes

- `InputFollow(formEl, params)` works on a `<form>` element; string values are resolved with `document.querySelector`
- Error state is observed through an `errors` proxy, which triggers `on_success` / `on_error` / `on_validate` / `on_submit` / `on_failed`
- Defaults live in `arrangedParams` in `src/index.ts` (`error_class: 'has-error'`, `valid_class: 'is-valid'`, `novalidate: true`, `initial_valid_view: false`, ...)
- Validation types: `required` / `email` / `number` / `code` / `hiragana` / `katakana` / `kana` / `hankaku-kana` / `alpha` / `alphanumeric` / `zen-alpha` / `zen-alphanumeric` / `['equal', 'field_name']` / `custom` (with `validate`)
- Input limiting types: `number` / `code`. Limiting is applied when validation runs (blur / submit), not on every keystroke
- Cross-field rules: `mode` (`or` / `and`) with `with`, group rules (`name: ['a', 'b']`) and conditional validation with `if` (`target`, string or boolean values)
- Constraints: `min` / `max`, `minlength` / `maxlength`, `pattern`; `type` can be omitted when only constraints are used
- Async validators: `async: true` + `validateAsync()`; form submit is prevented until they resolve
- Optional styles live in `styles/inputfollow.css` and are copied to `dist/inputfollow.css` by `postbuild`
- Avoid breaking changes and extend with additive options. Bump `package.json` version on a gitflow release branch
- `package.json` uses an `exports` map: `import` → `dist/index.es.js`, `require` → `dist/index.cjs`, `./inputfollow.css` → `dist/inputfollow.css`. The IIFE bundle (`dist/inputfollow.js`) is only for `<script>` tags and CDNs (`unpkg` / `jsdelivr`)
